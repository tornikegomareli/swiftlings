# Swiftlings — Designer Brief

## 1. What is this product?

**Swiftlings** is a terminal (CLI/TUI) tool for learning the Swift programming language, modeled directly on **Rustlings** (the well-known Rust learning tool). There is no GUI, no web app, no mouse — everything happens in a terminal window using text, ANSI colors, emoji, and single-keypress shortcuts.

The core loop: the tool shows the learner one broken Swift file at a time. The learner opens that file in their own code editor (VS Code, Xcode, etc. — outside the tool), fixes the code, saves it. Swiftlings **automatically detects the file save**, recompiles and re-runs it, and reports success or failure right there in the terminal. This "watch mode" is the primary experience — everything else (list, hint, reset commands) is secondary/supporting.

This brief documents every screen, state, button (keypress), and piece of content so a designer can mock up a TUI redesign — colors, layout, typography-in-terminal, spacing, iconography — without needing to read Swift code.

## 2. Platform constraints (important for design)

- **Terminal-only.** Monospace font, fixed character grid, no true pixel graphics. Only ANSI 16-color palette + emoji + box-drawing/ASCII characters are available.
- **No mouse.** Every interaction is a single keypress (raw/uncooked terminal input — key is captured the instant it's pressed, no Enter required, except in a couple of legacy prompts noted below).
- **Full-screen clear-and-redraw model.** The tool clears the entire terminal (`\x1B[2J\x1B[H`) and reprints the whole screen on every state change — there is no persistent split-pane/scroll region today. (A designer could propose a persistent-pane / status-bar layout as an improvement — worth calling out as an opportunity.)
- **Runs inside whatever terminal emulator the user has** (Terminal.app, iTerm2, Warp, VS Code integrated terminal, etc.) — width is NOT fixed, but the tool currently assumes ~80–120 columns (see `progressBarWidth = 120`, `defaultTerminalWidth = 80`).
- Colors currently used: **green** (success), **red** (error), **yellow** (warning), **blue** (info), **cyan** (progress / highlighted paths).
- Emoji currently used: 🦉 (owl mascot/logo), 🎉 (celebration), ✅ ❌ ⚠️ ℹ️ 🔄 (status icons), 💡 (hint/lightbulb), 🚀 (init/launch), 🎯 (DSA mode target icon), ⭐ (star the repo).

## 3. Who uses it / when

Swift beginners-to-intermediate developers, working through structured exercises at their own pace, exercise by exercise, in a terminal next to their editor. Sessions are long-running (the watcher stays open while they edit files back and forth).

## 4. Top-level commands (entry points)

Running `swiftlings <command>`. If no command is given, it defaults to **watch mode** (see §5 — this is the main app screen).

| Command | Purpose |
|---|---|
| `swiftlings` (no args) | Default — launches interactive Watch Mode |
| `swiftlings init` | One-time setup: clones/creates the exercises folder on disk |
| `swiftlings run [name]` | Run one exercise once, print result, exit (non-interactive, no watching) |
| `swiftlings hint [name]` | Print the hint text for an exercise, exit |
| `swiftlings list [--pending] [--completed]` | Print a static table of all exercises + status, exit |
| `swiftlings reset [name] [--all] [--progress-only] [--force]` | Reset exercise file(s) and/or saved progress |
| `swiftlings watch` | Same as running with no args |
| `swiftlings dsa` | Launches a separate "Data Structures & Algorithms" learning track (a menu, then watch mode filtered to that track) |
| `swiftlings --help` / `--version` | Standard CLI help/version (auto-generated by ArgumentParser, version currently `0.1.2`) |

## 5. Watch Mode — the main screen (design priority #1)

This is the screen the user stares at for 90% of their time in the tool. It re-renders fully every time: (a) the user saves the exercise file, or (b) the user presses a key.

### 5a. First-run welcome screen (only shown once, before the very first exercise)

Full-screen text, then waits for **any keypress**:

```
Welcome to Swiftlings! 🦉

Is this your first time? Don't worry, Swiftlings is made for beginners!
We are going to teach you a lot of things about Swift, but before we can
get started, here are some notes about how Swiftlings operates:

1. The central concept behind Swiftlings is that you solve exercises...
2. Exercises are organized into categories (like 00_basics, 01_control_flow, etc.)...
   • A README.md file with detailed explanations of the concepts
   • Links to official Swift documentation for deeper learning
   • 4-7 exercises that progressively build your understanding
3. Make sure to have your editor open in the project directory...
4. If you're stuck on an exercise: Enter 'h' to show a hint...
5. The exercises use a custom test framework (test() blocks, assertEqual())...
6. Have fun learning Swift! Remember: making mistakes is part of learning!

📌 Don't forget to ⭐ star the Swiftlings GitHub repository!

Press any key to start...
```

### 5b. The main loop screen — anatomy (top to bottom)

Every render of the main screen has these five zones, always in this order:

1. **Header banner** — one line, color-coded pass/fail state, plus an optional encouragement line:
   - Success state: `✅ Exercise done` (green) + `When done experimenting, enter 'n' to move on to the next exercise 🎉`
   - Failure state: `❌ Exercise failed` (red), no extra line
2. **Progress bar** — overall course completion, always visible:
   ```
   Progress: [########################>--------------------] 42/94 (45%)
   Current exercise: Exercises/01_control_flow/loops1.swift   ← shown in cyan
   ```
   (Bar uses `#` for filled, `>` as the leading edge, `-` for empty, in `[ ]` brackets. Default width 120 chars in watch mode, 10-block version `█`/`░` used in DSA menu — see §7.)
3. **Current exercise identity** — shown like a code comment, in a monospace "peek at the file" style:
   ```
   // loops1.swift
   // Use a for-in loop to iterate over the range and print each number
   ```
4. **Result / output panel** — content depends on the last run's outcome (see the 3 states below).
5. **Footer command bar** — always the same single line, always visible:
   ```
   n:next / h:hint / l:list / c:check all / x:reset / q:quit
   ```

### 5c. The three possible result states inside the "output panel" (zone 4)

**State A — Success**
```
Output

<any printed stdout from the exercise, if it produced output>
```
Header shows the green "Exercise done" banner above.

**State B — Compilation error**
```
❌ Compilation error:
<swiftc compiler error text — file/line/column, red squiggly-style text, can be multi-line>
```
Header shows the red "Exercise failed" banner above.

**State C — Test failure**
```
❌ Test failure:
<assertion failure message from the custom test framework, e.g. which assertEqual failed and expected vs actual>
```
Header shows the red "Exercise failed" banner above.

While a run is in progress (between file save and result), two transient status lines are printed (cyan, with 🔄):
```
🔄 Compiling loops1...
🔄 Running loops1...
```

### 5d. All-exercises-complete screen (terminal state)

```
🎉 Congratulations! You've completed all Swiftlings exercises!

🎉 Congratulations! You've completed all Swiftlings exercises!

We hope you enjoyed learning about Swift!
If you noticed any issues, don't hesitate to report them on GitHub.
You can also contribute your own exercises to help the community!
```
(No footer command bar — the app effectively idles/exits here.)

### 5e. Keyboard shortcuts inside Watch Mode (the actual "buttons")

All are single keypress, no Enter needed, case-insensitive:

| Key | Action | Resulting screen |
|---|---|---|
| `n` | Advance to next exercise | If current exercise passed: clears, loads & runs the next exercise (new full render). If current exercise has NOT passed: shows `⚠️  Complete the current exercise first` (yellow) for ~1.5s, then re-renders current screen. |
| `h` | Show hint | Full-screen takeover: `ℹ️  Hint for <name>:` (blue) + blank line + hint text + blank line + `Press any key to continue...` → any key returns to the main loop screen. |
| `l` | List all exercises | Full-screen takeover: `ℹ️  Exercise List` + progress bar + exercises grouped under bracketed category headers `[00_basics]`, `[01_control_flow]`, etc., each line prefixed `✓` (done) or `○` (not done), with `← current` suffix on the active one. Ends with `Press any key to continue...`. |
| `c` | Check all (batch re-run every pending exercise) | Full-screen takeover: `ℹ️  🔍 Checking all exercises...` then a live-appending list, one line per exercise: `✅ <name>` or `❌ <name> - compilation error` / `❌ <name> - test failure` / `❌ <name> - error: ...`. Ends with `Summary: N exercises need work` + `Press any key to continue...`. |
| `x` | Reset current exercise (or, inside DSA mode, offers to reset the whole DSA track) | Normal mode: `ℹ️  Resetting <name>...` → `✅ Exercise reset!` (1s pause) → re-render. DSA mode: inline y/n confirmation prompt `⚠️  Reset all DSA exercises? (y/n): ` (single keypress y confirms) → `ℹ️  Resetting all DSA exercises...` → `✅ All DSA exercises reset!` → jumps back to exercise #1 of the track. |
| `q` | Quit | Immediately exits the process, no confirmation. |
| any other key | (no-op) | Screen unchanged. |

## 6. Non-interactive command screens (one-shot output, then exits back to shell)

### `swiftlings list`
```
ℹ️  Progress: 42/94 (44.7%)

✓  intro1               00_basics
○  intro2               00_basics
...
```
Status column: `✓`(green, completed) or `○`(not done) — one row per exercise, exercise name padded to 20 chars, category padded to 15 chars, in fixed-width columns.
Flags `--pending` / `--completed` filter the rows and add a footer note (`ℹ️  Showing only pending exercises`, etc.). Always ends with `ℹ️  Run 'swiftlings run <exercise-name>' to run a specific exercise`.

### `swiftlings hint [name]`
```
ℹ️  Hint for 'loops1':

💡 Use a for-in loop to iterate over the range and print each number

```
If no name given, uses the learner's current exercise; if there is none, prints `ℹ️  No current exercise. Use 'swiftlings run' to start!`.

### `swiftlings run [name]`
Non-watching single execution — same visual language as Watch Mode's zones 1/4 but without progress bar/footer:
```
ℹ️  Running: loops1
File: Exercises/01_control_flow/loops1.swift

🔄 Compiling loops1...
🔄 Running loops1...
Output:
<stdout>

✅ Exercise loops1 completed successfully!
ℹ️  Next exercise: loops2
```
(Or the compilation-error / test-failure variants, ending with `ℹ️  Try again after fixing the errors!` / `ℹ️  Keep trying!` instead of "Next exercise".)

### `swiftlings reset`
Without `--force`, it's a plain-text confirmation gate (note: this one is NOT single-keypress, it just re-runs the command with the flag):
```
Are you sure you want to reset <exercise 'x' to its broken state | all exercises to their broken state and all progress | all progress>? This will lose any changes.
Use --force to skip this confirmation.
```
With `--force` (or after re-invoking with it), shows progress + success lines:
```
🔄 Resetting exercise: loops1...
✅ Exercise 'loops1' reset to original state
🔄 Resetting progress...
✅ Progress reset

ℹ️  Ready to start over! Run 'swiftlings' to begin.
```

### `swiftlings init`
```
🚀 Initializing Swiftlings project...
✅ Successfully initialized Swiftlings project in 'swiftlings'!

To get started:
  cd swiftlings
  swiftlings

Or run a specific exercise:
  swiftlings run <exercise-name>

For help:
  swiftlings --help
```
Failure states: directory-already-exists (`❌ Directory 'swiftlings' already exists!` + `💡 Use --force to overwrite...`) or git-clone failure (`❌ Failed to clone exercises repository` + stderr).

## 7. DSA Mode (`swiftlings dsa`) — a distinct sub-product

A separate learning track ("Data Structures & Algorithms") with its own selection menu, then it re-enters Watch Mode filtered to only that track's exercises.

**Selection menu screen:**
```
Welcome to Swiftlings DSA Mode! 🎯
=====================================

Master Data Structures & Algorithms through hands-on implementation.

Available Data Structures:

  1. Queue [██████░░░░] 60% (3/6)
     FIFO data structure - First In, First Out
     6 exercises

Select a data structure (1-1) or 'q' to quit:
```
Note: this progress bar uses a **different visual style** than the main progress bar — solid/light blocks `█`/`░` in a compact 10-segment bar with a percentage, vs. the `#`/`-`/`>` ASCII bar elsewhere. This inconsistency is worth flagging to the designer as something to unify.

This screen requires typing a number **and pressing Enter** (it's a `readLine()` prompt, not raw single-keypress — an inconsistency vs. every other screen in the app, also worth flagging).

Currently only **1 data structure** is live (Queue, 6 exercises); the code already anticipates future entries (Stack, Linked List, Binary Tree, Graph) as a growing numbered list — the designer should design this menu to scale to 5+ rows.

After selecting, a short transition screen:
```
Starting Queue exercises...

You'll be working through 6 exercises.
The watch mode will guide you through each one.

Press any key to begin...
```
...then it's the exact same Watch Mode UI as §5, just scoped to only Queue exercises (and the `x` reset key behaves differently as noted in §5e).

## 8. Content taxonomy / data the designer should know about

- **94 total exercises** across **19 numbered core categories** (00–18) plus **1 DSA category** (20_dsa_queue), e.g.:
  - `00_basics` (11 exercises), `01_control_flow` (7), `02_functions` (5), `03_collections` (5), `04_optionals` (4), `05_structs` (4), `06_classes` (4), `07_enums` (4), `08_protocols` (4), `09_extensions` (4), `10_generics` (4), `11_error_handling` (4), `12_closures` (4), `13_memory_management` (4), `14_property_wrappers` (4), `15_concurrency` (4), `16_result_builders` (4), `17_advanced_types` (4), `18_codable` (4), `20_dsa_queue` (6, in a separate mode).
- Each **exercise** has: a `name` (e.g. `loops1`), a `dir`/category, a `hint` (one sentence), a `.swift` source file, and a completion boolean.
- Each **category** additionally has its own `README.md` with a title, links to official Swift docs, and a concept summary — currently these are never shown inside the TUI itself (only exist as files the user reads in their editor). This could be an area the designer chooses to surface inside the tool (e.g. an in-app "read the concept" panel).
- **Progress** is a simple `completed / total` count + percentage, tracked persistently (stored in a local dotfile), survives restarts.
- **Exercise state** is one of exactly three outcomes after each run: **success**, **compilation error**, **test failure** — every screen that shows a result reduces to these three cases. Never any "in between"/partial-credit state.
- There's also a global concept of **"current exercise"** (a single pointer — the next unsolved exercise in sequence, or the one explicitly picked with `run <name>`).

## 10. Known inconsistencies worth the designer addressing

1. Two different progress-bar visual styles exist (`#`/`-`/`>` ASCII vs. `█`/`░` blocks) — should be unified into one system.
2. Most of the app is single-keypress/no-Enter, but the DSA menu requires typing+Enter — inconsistent interaction model.
3. Full-screen clear-and-redraw everywhere — no persistent chrome (e.g., an always-visible header/status bar that doesn't flash/redraw), no scrollback-friendly layout. A redesign could introduce a fixed top status bar + scrolling log area, similar to htop/lazygit-style TUIs.
4. Category README content (concept explanations, doc links) is invisible to the TUI — currently the user must alt-tab to their editor to read it.
5. No visual distinction in the exercise list between "current" and "completed-out-of-order" beyond `✓`/`○` + a text arrow — a designer may want icons/color instead.
6. No color legend/help screen exists in-app; colors are load-bearing for meaning (red=fail, green=pass) which may need an accessible/no-color fallback mode.

## 11. Suggested deliverables for the designer

Given the above, useful TUI mockups to produce:
1. Watch Mode — success state, compilation-error state, test-failure state (the 3 core screens, seen most often).
2. Welcome / onboarding screen.
3. Hint overlay, List overlay, Check-all overlay.
4. All-complete celebration screen.
5. DSA selection menu (scaled to show 5 data structures, to prove it scales).
6. A persistent header/status-bar concept exploring an alternative to full-screen redraw (optional stretch/improvement proposal).
7. A color + iconography legend/style guide (success/error/warning/info/progress + the emoji set) so it's consistent across every screen above.
